= SoftNavContext integration for Antora extensions

Third-party scripts should prefer `SoftNavContext` when present and fall back to SoftNav or full page load.

See link:ARCHITECTURE.adoc[ARCHITECTURE.adoc] for the three-layer model (SoftNav transport → SoftNavContext store → `bindSoftNavContext` helper).

== Load order

1. `soft-nav.js`
2. `soft-nav-context.js`
3. `bind-soft-nav-context.js` (optional helper)
4. Feature scripts (search, Mermaid, nav-tree, …)

The Antora extension injects (2) and (3) after `soft-nav.js` in `footer-scripts` or `footer-content`, or after `site.js` when SoftNav is not registered yet.

== Page context (build time)

Register `@antora-supplemental/soft-nav-context` on the playbook. The extension injects partial `soft-nav-page-context` into `article` and ships runtime JS.

Each published page exposes `#soft-nav-page-context` (`data-*` attributes). SoftNav fetches the next page; SoftNavContext parses that node from `detail.doc` and updates `SoftNavContext.context`.

== Event order (successful navigation)

[cols="1,2"]
|===
| Phase | When

| `before` | SoftNav is about to fetch; flush scroll / prep nav
| `context` | Parsed page metadata updated (`SoftNavContext.context`); use for persistent chrome
| `loaded` | Regions applied; `detail.doc` available; use for rebind / innerHTML refresh
|===

DOM mirrors: `soft-nav-context:before`, `:context`, `:loaded`, `:failed`.

== Extension pattern (vanilla)

[source,javascript]
----
bindSoftNavContext({
  onBoot: function () { boot(document) },
  onContext: function (ctx) { syncFromContext(ctx) },
  onLoaded: function (nav) { boot(nav.articleHost || document) },
})
----

`onContext` requires `soft-nav-context.js`. Without it, use `onLoaded` and read `detail.doc` only.

== DOM events

Same phases as `SoftNavContext.on`, prefixed `soft-nav-context:` (detail = context or nav ctx).

See link:NAMING.adoc[NAMING.adoc] for `valentus-` theme hooks vs this runtime.
