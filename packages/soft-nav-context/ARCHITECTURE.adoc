= SoftNav, SoftNavContext, and extension lifecycle

Three layers solve different problems. **Persistent chrome** should use layer 2 signals first; layer 3 is convenience for boot and `loaded`.

== Layer 1 — SoftNav (transport)

*Package:* `antora-ui-chassis/packages/soft-nav` (Antora inject or copy `soft-nav.js`).

* Intercept same-component links, fetch HTML, swap regions (`mast`, `nav`, `article`)
* Phases: `before` → fetch → `loaded` | `failed`

SoftNav does **not** know about search scope or breadcrumbs.

== Layer 2 — SoftNavContext + SoftNavSignals (canonical chrome store)

*Package / extension:* `@antora-supplemental/soft-nav-context`.

Responsibilities:

* Parse page metadata from each document (`#soft-nav-page-context`, search-chat `data-*` fallback)
* Hold `SoftNavContext.context` for navbar / dock / scope UI that SoftNav does not replace
* **`SoftNavSignals`** — subscribe per field; one batched notification wave per context update

=== Signal API (extension authors — start here)

Global: `SoftNavSignals` (same object as `SoftNavContext.signals`).

[cols="1,2"]
|===
| Method | Purpose

| `get(key)`
| Current value for a derived key

| `subscribe(key, fn)`
| `fn(value, fullContext)` on subscribe (immediate) and whenever context changes after navigation

| `subscribeContext(fn)` / `subscribe(fn)`
| Shorthand for full context object (`key === 'context'`)

| `keys()`
| List of supported keys
|===

Derived keys (from parsed context):

* `context` — full normalized object
* `pageUrl`
* `componentName`, `componentTitle`
* `versionName`, `versionDisplay`
* `scopeLabel` — human hint from component + version (e.g. for omnibox chrome; not the user's Lunr scope selection)

On each successful in-component navigation:

[source]
----
soft-nav:before
soft-nav:loaded → setContext(doc) → soft-nav-context:context (phase)
                 → SoftNavSignals batch (all keys, stable order)
                 → soft-nav-context:loaded (nav ctx with doc)
----

On first full page load, context and signals seed from the current document before any navigation.

Phase API (`SoftNavContext.on('before'|'context'|'loaded'|'failed')`) remains for transport-aligned work and DOM events (`soft-nav-context:*`).

== Layer 3 — `bindSoftNavContext` (lifecycle convenience)

*File:* `js/bind-soft-nav-context.js`.

Maps `onContext` → `SoftNavSignals.subscribe('context', …)` when signals exist. Use for:

* `onBoot` — first paint when signals are not enough (article-only scripts)
* `onBefore` / `onLoaded` — SoftNav transport (`detail.doc`, region hosts)

Do **not** treat `onContext` alone as the primary API — prefer explicit `SoftNavSignals.subscribe('componentName', …)` (or `subscribeContext`) in feature code.

== Without signals, why not only `SoftNav.on('loaded')`?

`loaded` is correct for *swapped article* work. Persistent chrome needs metadata from the fetched page **before** every consumer re-parses `#soft-nav-page-context` from `detail.doc`. Signals give one parse, one broadcast, derived fields for labels — not an interim pattern until a “real” framework.

A Preact/React island or article-only Mermaid rebinding still does not need signals. Navbar search scope, dock context, and path-aware chrome do.
