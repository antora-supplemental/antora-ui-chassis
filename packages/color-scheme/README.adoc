= Color scheme (`packages/color-scheme`)

The color scheme layer for Antora UIs: the `--cs-*` token contract that layouts and paints meet on, the *color schemes* a paint declares (light and dark slots, a picker page when a paint has more than two), and opt-in *live paint* (swap the whole paint for previews). It sets no colors.

*Looking for dark mode?* Light/dark switching (no-flash hook, saved choice, system preference, the toggle) moved to link:../light-dark-mode/README.adoc[`@antora-supplemental/light-dark-mode`] in 0.3.0. It registers this package, so most sites list only that one. Upgrading from 0.1/0.2 or from `antora-dark-mode`: link:https://github.com/antora-supplemental/antora-ui-chassis/blob/main/docs/modules/ROOT/pages/migrate-dark-mode.adoc[Migrating dark mode to the chassis].

== Install

[source,yaml]
----
antora:
  extensions:
    - require: '@antora-supplemental/color-scheme'
      slots: { ... }        # optional, see Color schemes
      live_paint: { ... }   # optional preview feature, see below
----

[source,json]
----
"@antora-supplemental/color-scheme": "github:antora-supplemental/antora-ui-chassis#color-scheme-v0.5.2&path:packages/color-scheme"
----

The extension links `css/color-scheme.css` after `site.css`. When the active paint declares more than two schemes (or the site sets slots or forces the picker) it also inlines the schemes head hook and loads `js/color-scheme.js`; `live_paint` adds the paint head hook.

== Token contract (`--cs-*`)

The mechanism sets no colors. Paints define these for light (`:root`) and dark (`html.dark-theme`); layouts and extensions read `var(--cs-name, system-color)`:

[cols="1,3"]
|===
| core | `--cs-canvas`, `--cs-elevated`, `--cs-ink`, `--cs-ink-muted`, `--cs-border`, `--cs-accent`
| accents | `--cs-accent-hover`, `--cs-accent-soft`, `--cs-hover`
| code | `--cs-code-bg`, `--cs-code-fg` (listing / pre blocks)
| callouts | `--cs-admonition-note`, `-tip`, `-important`, `-warning`, `-caution`
|===

The six core tokens are also published as `--valentus-canvas`, `-elevated`, `-ink`, `-ink-muted`, `-border`, `-accent`; existing extensions read those names, and they remain part of the contract. Paints that implement it: `@antora-supplemental/default-paint`, Valentus Paint.

== Paint validator

`scripts/validate-paint.mjs` checks that a paint styles only shared hooks (token blocks, Default UI chrome, Asciidoctor content, highlight.js, the light-dark-mode toggle):

[source,console]
----
node scripts/validate-paint.mjs path/to/paint.css [--extra=.my-layout-] [--strict] [--json]
----

Layout classes not on the allowlist, `@import` and external `url()` are errors. Literal colors outside token blocks are warnings, errors with `--strict`. `--extra` takes the layout prefixes a paint declares (registry manifest `paint.extraSelectors`). Exit code 0 means pass.

== Color schemes

A paint declares the color schemes it provides. Every paint has `light` and `dark`; a paint can add more (sepia, high contrast, a brand tint). The site's `light` and `dark` *slots* each hold one of those schemes, and `light-dark-mode` switches between the two slots.

The paint declares its schemes in a manifest comment at the top of its stylesheet:

[source,css]
----
/* @color-schemes
{
  "light": { "label": "Light" },
  "dark": { "label": "Dark" },
  "sepia": { "label": "Sepia", "slots": ["light"] },
  "midnight": { "label": "Midnight", "slots": ["dark"] }
}
*/
:root { ... }                              /* light */
html.dark-theme { ... }                    /* dark */
html[data-scheme="sepia"] { ... }          /* drawn on light */
html.dark-theme[data-scheme="midnight"] { ... }
----

* `slots` says which light/dark slots a scheme is a candidate for: `"light"`, `"dark"`, `"both"` (or a list), or `"none"` (`[]`) for a scheme not made for the light/dark system. Default both; `light` and `dark` fit their own. `base` is the light/dark state it is drawn on (default: `dark` when it fits only dark, else `light`).
* The active paint is the last stylesheet in `head-styles` with a manifest. A paint without one provides `light` and `dark` only. `default-paint` and Valentus Paint declare exactly those two.
* The runtime sets `html[data-scheme="<id>"]`; the scheme's CSS keys off that, and light/dark still sets `html.dark-theme`.

[source,yaml]
----
    - require: '@antora-supplemental/light-dark-mode'
      color_scheme:
        schemes:                # optional: add, relabel or drop (false) paint schemes
          sepia: { label: Old paper }
        slots: { light: sepia, dark: dark }   # site defaults; must be schemes of the active paint
        slot_policy: declared   # declared (default): a scheme goes only in slots it lists; any: a light/dark/both scheme fits either slot (none never)
        picker: auto            # auto (default): on when the paint has more than 2 schemes; true | false
        # picker: { enabled: true, placement: footer, label: Color schemes, preview_page: index.html, labels: { reset: Reset to defaults } }
        #   placement: footer (link in the footer) | none (build the page, place the link yourself)
        scheme_param: scheme    # ?scheme=<id>; ?scheme=auto turns automation on; ?scheme=reset restores default slots
        scheme_cookie: cs-scheme
----

With only `light` and `dark` and the default slots, nothing is added: no head hook, no runtime, no footer link. Scheme ids are lowercase letters and digits (Antora camelCases playbook keys). Unknown slot values, bad slots and unfitting slots fail the build.

=== Slots and light/dark automation

A visitor can reassign the slots (saved in the `cs-scheme-slots` cookie for a year).

* A `light`, `dark` or `both` scheme is only a slot candidate. Choosing it puts it in the current mode's slot when it fits (a `both` scheme always does), else in the slot it declares (picking Midnight in light mode makes it the dark scheme). Light/dark automation is never turned off by it, under either `slot_policy`.
* Only a scheme with slot `none` is an *off-slot pick*: it is pinned for the session (session cookie `cs-scheme`, gone when the browser closes) and light/dark automation turns off, pinned to the scheme's `base`. The toggle shows that state (navbar `aria-pressed="mixed"`, footer note). A `none` scheme can never fill a slot.
* Choosing any slot scheme, Light, Dark or Auto, or `?scheme=auto`, turns automation back on. `?scheme=reset` also restores the site's default slots.

=== Picker page

When the picker is on, the build adds a `color-schemes.html` page to the start page's component version, rendered in the UI's default layout (site header, nav, footer and light/dark toggle; it falls back to a standalone `_/color-schemes.html` only without a start page). The page lists schemes, never paints, in up to three sections, each a horizontal row of cards (live thumbnail and name) that is a `radiogroup` (arrow keys, Home and End move and select; the selected card is filled):

* *Light mode*: `light` and every scheme that fits the light slot. Picking one sets the light slot.
* *Dark mode*: `dark` and every scheme that fits the dark slot. A `both` scheme appears in both rows.
* *Neither*: `none` schemes. Picking one uses it for this visit only and turns automatic light/dark off.

Empty sections are hidden. Thumbnails are iframes of `preview_page` with `?cs-preview=<id>&cs-preview-mode=light|dark`, which never write cookies. *Reset to defaults* clears the visitor's slots and session scheme, restores the site's default slots and turns automatic light/dark back on.

All page text comes from `picker.labels` (for translation), each key optional, plain strings up to 300 characters: `intro`, `reset` (default "Reset to defaults"), `back`, `light`, `lightNote`, `dark`, `darkNote`, `none`, `noneNote`, `sessionOn` (`{scheme}` is replaced by the scheme's label). Unknown keys fail the build.

The footer link is the `color-scheme-picker-link` partial, with a chain-link icon from the `color-scheme-picker-link-icon` partial (inline SVG in `currentColor`, 1em, `aria-hidden`; the link text is the accessible name). Override order for either partial: your supplemental UI, then the theme, then the chassis default. An empty `color-scheme-picker-link-icon` partial removes the icon. `placement: footer` includes it in `footer-content` unless a partial already does; `placement: none` leaves it to you.

[source,js]
----
ColorScheme.schemes()            // [{ id, label, slots, base }]
ColorScheme.getScheme()          // active scheme id (also html[data-scheme])
ColorScheme.setScheme('sepia')   // false for unknown ids; null or 'auto' = automation on; 'reset' = default slots
ColorScheme.assign('dark', 'midnight')   // false when the scheme does not fit the slot
ColorScheme.slots()              // { light, dark }
ColorScheme.offSlot()            // { id, base } while a slot-none scheme is pinned
document.addEventListener('color-scheme:scheme', (e) => e.detail.scheme)
UiBus.state.watch('color-scheme.scheme', (id) => {})
----

== Live paint (opt-in preview)

Swaps the whole paint stylesheet at view time, so one prebuilt page can show several paints (registry previews, paint demos). Off by default. It has no slots and no picker UI; it is separate from color schemes (a live-painted page still shows that paint's schemes).

[source,yaml]
----
      color_scheme:
        live_paint:
          enabled: true
          param: paint          # ?paint=<id>; ?paint=reset clears the saved choice
          cookie: cs-paint      # SameSite=Lax, Path=cookie_path (default /), one year
          paints:               # the only paints that can load
            default: css/default-paint.css
            valentus: { href: 'https://cdn.example.org/valentus/4.0.0/site-paint.css', label: Valentus }
          allow_origins: [https://registry.antora-supplemental.org]   # postMessage senders
----

* `live_paint.slots`, `slot_policy`, `picker` and per-paint `slots`/`base` (0.3.0) fail the build with a pointer to the top-level options.
* Paint ids are lowercase letters and digits. Bad ids, `javascript:`/`data:` hrefs, quotes and malformed origins fail the build.
* Order: query, then cookie, then the site's built-in paint. An unknown id is ignored (an unknown cookie is cleared). The query never carries a URL.
* A built-in paint `<link>` whose file matches a map entry is the *base*: it is disabled while another paint is active and reused when its own id is chosen.
* `html[data-color-scheme-paint]` names the active live paint.

[source,js]
----
ColorScheme.paints()             // ['default', 'valentus']
ColorScheme.getPaint()           // null = built-in
ColorScheme.setPaint('valentus') // false for unknown ids; null or 'reset' = built-in
document.addEventListener('color-scheme:paint', (e) => e.detail.paint)
----

From an allow-listed parent:

[source,js]
----
frame.contentWindow.postMessage({ type: 'color-scheme:paint', id: 'valentus' }, siteOrigin)
frame.contentWindow.postMessage({ type: 'color-scheme:scheme', id: 'sepia' }, siteOrigin)
frame.contentWindow.postMessage({ type: 'color-scheme:assign', slot: 'dark', id: 'midnight' }, siteOrigin)
frame.contentWindow.postMessage({ type: 'color-scheme:mode', mode: 'dark' }, siteOrigin)
// replies { type: 'color-scheme:state', paint, paints, scheme, schemes, slots, offSlot, mode, dark }; on load the frame posts color-scheme:ready
----

In a cross-site iframe browsers usually drop the cookie, so pass `?paint=<id>` or `?scheme=<id>` in the `src` or use `postMessage`.
