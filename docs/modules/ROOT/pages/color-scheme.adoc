= Dark mode and color schemes
:description: How the chassis does dark mode (light/dark switching) and color schemes, and where antora-dark-mode went.
:keywords: dark mode, light mode, antora-dark-mode, color scheme, theme toggle

Dark mode on an Antora site takes three layers:

* `@antora-supplemental/light-dark-mode` (chassis): switches light and dark. No-flash head hook, saved choice, system preference, and the toggle as a top-bar icon button (`toggle_placement: navbar`) or a footer Light / Dark / Auto switch (`toggle_placement: footer`). Package README: `packages/light-dark-mode/README.adoc`.
* `@antora-supplemental/color-scheme` (chassis): the `--cs-*` token contract, the color schemes a paint declares (light/dark slots, a picker page when a paint has more than two), and optional live paint for previews. Package README: `packages/color-scheme/README.adoc`.
* Paint: the colors. `@antora-supplemental/default-paint` for the Default UI (xref:default-paint.adoc[]), Valentus Paint for Valentus.

To check every scheme for contrast in CI see xref:contrast-check.adoc[].

`antora-dark-mode` 2.x is built here (`packages/antora-dark-mode`) and registers all three. Upgrading: xref:migrate-dark-mode.adoc[].

== Override order

For every piece of dark-mode markup (toggle button, footer switch, picker link) the highest wins:

. your site's supplemental UI (a partial with the same name, or markup you placed),
. the theme or layout (Valentus ships its own `light-dark-toggle`),
. the chassis default.

The chassis never replaces icons or buttons it was given.

== Options

[cols="1,3",options="header"]
|===
| Option | Meaning
| light-dark-mode `toggle` | `auto` (default) creates the toggle when the layout placed none; `placed` binds only
| light-dark-mode `toggle_placement` | `navbar` (default) or `footer`
| light-dark-mode `follow_system` | `true` (default); `false` starts in light and ignores the OS
| light-dark-mode `navbar` | `<meta name="dm-navbar">` value for paint
| light-dark-mode `color_scheme` | options passed to color-scheme
| paint `/* @color-schemes {json} */` | the schemes the paint provides: `{ <id>: { label, slots: [light, dark], base } }`; `light` and `dark` always exist
| color-scheme `schemes` | add, relabel or drop (`false`) paint schemes
| color-scheme `slots` | `{ light: <scheme>, dark: <scheme> }` (default `light`, `dark`)
| color-scheme `slot_policy` | `declared` (default) or `any`
| color-scheme `picker` | `auto` (default, on when the paint has more than 2 schemes), `true`, `false`, or `{ enabled, placement: footer|none, label, preview_page, labels }`. The picker page has Light mode, Dark mode and Neither sections of scheme cards and a *Reset to defaults* button; `labels` overrides every string on it. The footer link carries a chain-link icon (`color-scheme-picker-link-icon` partial, overridable like the link)
| color-scheme `live_paint.paints.<id>` | preview only: href, or `{ href, label }`
| query | `?scheme=<id>`, `?scheme=auto`, `?scheme=reset`; `?paint=<id>`, `?paint=reset` (live paint); `?cs-preview=<id>&cs-preview-mode=light|dark` (preview only, no writes)
|===

Choosing a `light`, `dark` or `both` scheme only puts it in a slot; automation stays on. Only a scheme with slot `none` (not made for light/dark) turns light/dark automation off for the session. The navbar button then reports `aria-pressed="mixed"` and its label says so; the footer switch shows a note. Choosing Light, Dark, Auto or a slot scheme turns automation back on.

== Parity with antora-dark-mode 1.4.6

The chassis packages (light-dark-mode for the mechanism since color-scheme 0.3.0) replace `antora-dark-mode` 1.x. Every row must be equal or better before the old package is retired.
"Layer" says where the old behavior now lives: *chassis* (this package, no colors), *body kit* (Valentus places and dresses the toggle), *paint* (palette colors).

== Where antora-dark-mode went

`antora-dark-mode` 2.0.0 is published from this repository (`packages/antora-dark-mode`) as a thin Antora extension over light-dark-mode, color-scheme and default-paint. The old repository is a compatibility path: its UI bundle and git installs keep working, forward to the chassis and log one warning per build with the one-line migration. Nothing is archived or deprecated. See xref:migrate-dark-mode.adoc[].

== CSS short-circuit fallbacks

Chassis names the `--valentus-*` tokens; paint defines them for both schemes.
Every consumer (chassis components, body kit, paint users, bolt-ons) styles with:

----
color: var(--valentus-ink, CanvasText);
background: var(--valentus-canvas, Canvas);
----

so a region yanked out of the stack still paints something readable.

== Token contract and paint validation

Layouts and paints meet at the `--cs-*` contract: core `--cs-canvas`, `-elevated`, `-ink`, `-ink-muted`, `-border`, `-accent`; `--cs-accent-hover`, `-accent-soft`, `-hover`; `--cs-code-bg`, `-code-fg`; `--cs-admonition-note`, `-tip`, `-important`, `-warning`, `-caution`. Paints set them on `:root` and `html.dark-theme`; layouts read `var(--cs-*, system color)`. The six `--valentus-*` core names are aliases that stay in the contract.

Any contract layout works with any contract paint: Valentus Layout with `default-paint`, or the Default UI with Valentus Paint.

The registry checks a paint with `packages/color-scheme/scripts/validate-paint.mjs <css> --extra=<declared prefixes>`: layout classes outside the allowlist, `@import` and external `url()` fail; literal colors outside token blocks warn (`--strict` fails).

== Live paint and registry previews

`color-scheme` (0.2.0 and later) can swap the paint of a built site at view time (`live_paint`, off by default). Since 0.4.0 live paint is only this preview feature: the picker page lists the active paint's color schemes, never paints. Options and API: `packages/color-scheme/README.adoc`.

Security: only ids from the playbook `paints` map load, hrefs are validated at build time, and `postMessage` is accepted only from `allow_origins`. A page URL can pick a paint but never name a stylesheet.

=== Recipe: "this paint on this layout" demo site

. Build one demo site per layout (Default UI, Valentus Layout, ...) from the same demo content, with `color-scheme` and `live_paint.enabled: true`. List every registry paint in `paints`, pinned to a released URL (`https://cdn.jsdelivr.net/gh/<org>/<repo>@<tag>/<path>.css`) or copied into the UI as `css/<id>.css`.
. Set `allow_origins` to the registry origin and publish each demo statically (GitHub Pages).
. The registry embeds `<iframe src="https://demos.example.org/<layout>/index.html?paint=<id>">` and switches with `postMessage({ type: 'color-scheme:paint', id }, demoOrigin)` and `{ type: 'color-scheme:mode', mode: 'dark' }`; it listens for `color-scheme:ready` / `color-scheme:state`.
. Adding a paint means one map entry and one rebuild of the demo sites, not a build per pairing.

Only paints that style through the shared token contract and standard Antora/Asciidoctor classes look right on every layout; check paint CSS against a selector allowlist before listing it.

Verified 2026-10-25 on the Default UI with `default`, a recoloured variant and the current Valentus `site-paint.css`: the chosen paint is active at the first animation frame, `?paint=` beats the cookie, `reset` and raw URLs behave as above, an allow-listed iframe parent switches paint and mode, and a non-listed origin is ignored. axe shows no new violations for `default` or the variant; the pre-split Valentus paint adds contrast failures on this layout because it does not follow the contract yet.
